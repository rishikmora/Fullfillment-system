Differentiation

What makes this stand out

Most tutorial projects demonstrate concepts. This one demonstrates production thinking — the gap between code that works and code that survives real load.

01

Two-layer concurrency safety

Redis DECRBY is atomic — no two requests can simultaneously read the same stock level and both succeed. If the result goes negative, a race is detected and the order reroutes instantly. PostgreSQL SELECT FOR UPDATE then serializes the final reservation at the DB layer. Belt and suspenders — the same pattern Amazon uses in their inventory systems.

02

Domain-accurate routing math

Uses the Haversine great-circle formula — not Euclidean distance — to score warehouses. Euclidean distance is meaningless on a sphere; Haversine gives the actual flight-path distance. The algorithm is O(n) per order and provably correct for the nearest-warehouse problem on India-scale geography.

03

Cache-aside with intelligent fallback

Redis serves as the live inventory source of truth with a 5-minute TTL. On a cache miss — whether from expiry or a Redis restart — the system transparently falls back to PostgreSQL, warms the cache, and continues without any downtime. The application degrades gracefully even if Redis is completely unavailable.

04

Event-driven reorder pipeline

After every dispatch, stock levels are checked against a configurable threshold. If stock drops below it, a reorder_triggered event is published to a dedicated Kafka topic. This mirrors Amazon's automated replenishment system — the warehouse doesn't need a human to notice low stock, the system detects and signals it automatically.

05

91% test coverage, zero infrastructure

53 tests run in under 1 second with no Docker, no Postgres, no Redis required. All external dependencies are mocked with precise fixtures. GitHub Actions enforces an 85% coverage floor — if coverage ever drops below that, the CI pipeline blocks the merge. Coverage can never silently regress.

06

Kafka producer hardening

The Kafka producer is configured with acks=all and enable_idempotence=True — the strongest durability guarantee available. Orders are keyed by order_id so all events for one order land on the same partition, preserving per-order event ordering. Reorder events use best-effort delivery and swallow errors gracefully — a dropped reorder alert is recoverable; a dropped order event is not.

Engineering Rationale

Every decision, explained

Each component was chosen deliberately. Here is the reasoning behind every major architectural choice.

Component
Choice
Why not the alternative
Inventory reads
Redis DECRBY (atomic)
A DB read + check + write is three separate operations — a race window exists between them. Redis DECRBY is a single atomic operation.
Order events
Kafka with acks=all
Direct DB writes couple order placement to downstream processing. If the dispatch service is slow, all orders block. Kafka decouples them entirely.
Distance metric
Haversine great-circle
Euclidean distance treats the Earth as flat. At 1000km+ between Indian cities, the error is significant. Haversine is correct for geographic routing.
Cache pattern
Cache-aside (lazy loading)
Write-through keeps cache and DB perfectly in sync but every write is slower. Cache-aside is simpler and resilient — the DB is always authoritative.
DB concurrency
SELECT FOR UPDATE
Optimistic locking requires retry logic on conflict. Pessimistic locking (FOR UPDATE) is simpler and correct for low-contention inventory reservations.
Test DB
SQLite (file-based)
In-memory SQLite has connection isolation issues — tables created on one connection aren't visible on another. File-based SQLite avoids this entirely.
Framework
FastAPI + Pydantic v2
Auto-generated OpenAPI docs, async-native, Python type hints as the schema source of truth. Pydantic v2 is 5-50x faster than v1 for validation.

What is specifically tested

// routing

Haversine correctness

Mumbai→Delhi distance verified against known values. Symmetry property (A→B = B→A). Zero distance for same point. Chennai→Hyderabad range check.

// redis

Atomic operations

DECRBY returns new value on hit, None on miss. Negative result detection for race condition. Error swallowing so Redis outages don't crash the app.

// kafka

Producer hardening

Order events go to the correct topic. order_id used as partition key. KafkaConnectionError propagates for order events, swallowed for reorder events.

// service

Business logic

Successful orders update DB status and publish Kafka event. Failed orders record failure reason. Reorder trigger fires below threshold, not above it.

// api

Endpoint contracts

Input validation rejects quantity=0 and invalid coordinates. 404 on missing resources. Metrics endpoint serves from cache when available. Inventory available = quantity − reserved.

// ci

Automated pipeline

Every push runs the full test suite, lints with ruff, builds the Docker image, and smoke-tests the container. PRs cannot merge below 85% coverage.

Known Tradeoffs

Limitations & what comes next

Every system has tradeoffs. These are the ones made deliberately, with full awareness of what would need to change at production scale.

  • Design tradeoff

    Synchronous order routing

    The HTTP response waits for routing to complete. At Amazon scale, POST /orders would return PENDING immediately and routing would happen asynchronously via a Kafka consumer worker pool. The client would poll or receive a webhook. This was kept synchronous here for simplicity and demo-ability.

  • Scale gap

    Single-item greedy routing

    The current algorithm is optimal for single-product orders. Multi-product orders with split-shipment logic (where items might come from different warehouses) would require a linear programming or ILP optimizer. The greedy nearest-warehouse approach cannot minimize shipping cost across multiple items simultaneously.

  • Out of scope

    No authentication or authorization

    All endpoints are publicly accessible. A production system would layer JWT Bearer tokens on every endpoint, with role-based access control separating customer-facing APIs from warehouse management APIs. This was omitted to keep the demo focused on the routing and concurrency logic.

  • Scale gap

    No geographic sharding

    All warehouses are served by a single routing service. At Amazon's scale, India alone would have regional routing services (North, South, West, East) each with their own Redis cluster, so a Bangalore order never crosses a network boundary to reach a Mumbai routing service. The current flat architecture is correct but wouldn't scale beyond a few hundred warehouses.

  • Design tradeoff

    No circuit breakers

    If Redis becomes unavailable, the system falls back to PostgreSQL for every read — which works but at significantly higher latency. A circuit breaker (e.g. the Resilience4j pattern) would detect Redis degradation and automatically open the circuit, routing all traffic to DB until Redis recovers, rather than taking a latency hit on every single request during the outage window.

  • Out of scope

    No distributed tracing

    In production, every request would carry a trace ID (via OpenTelemetry) propagated through FastAPI, into Kafka messages, and through any downstream consumers. Without this, debugging a failed order requires manually correlating logs across services by timestamp — painful at scale.

  • Design tradeoff

    PostgreSQL over DynamoDB

    Amazon's actual inventory system uses DynamoDB — lower write latency, better horizontal scaling, native TTL. PostgreSQL was chosen here because it's more universally understood and easier to inspect during development. The data model and access patterns are compatible with a DynamoDB migration.

Getting Started

Local setup

Prerequisites

Python 3.12+ and Docker Desktop.

1 — Start infrastructure

docker-compose up postgres redis zookeeper kafka -d
# Wait ~30 seconds for Kafka to initialize
docker-compose ps   # all services should show healthy

2 — Install & configure

python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env              # defaults match Docker Compose

3 — Seed & run

python -m scripts.seed_db         # 5 warehouses + 5 products
uvicorn app.main:app --reload     # http://localhost:8000/docs
